# Task1 扩展说明：整网泛化新模型接入

## 1. 文档目的

本文面向后续开发者，说明如何在当前工具中接入新的语言类模型，使其参与 **Task1 整网泛化变异测试**，并按需打通 `pta_msa` 与 `pta_mf` 两条执行链路。

本文的目标不是重复介绍实现细节，而是给出一条更清晰、可维护的接入路径：**先跑通整网变异，再逐步补齐脚本生成、参数变异和静态图支持**。

---

## 2. Task1 的主链路

Task1 的核心入口位于 `utils/task/task1.py`。一轮完整流程通常包括：

1. `run_mutate()`  
   通过 `scripts/mutation/mutate-auto.sh` 调用 `utils/runtime/mutate_and_forward/mutate_graph-auto.py`，生成本轮整网变异结果。

2. `generate_pta_script()`  
   根据 `mutating-<iter>.json` 和模型模板脚本，生成实际可执行的 PTA 训练脚本。

3. `convert_msa_script()`  
   将 PTA 脚本转换为 MSA 脚本，形成 `pta_msa` 对比链路。

4. `generate_mf_script()`（可选）  
   将 PTA 脚本转换为 MindFormers YAML，用于 `pta_mf` 链路。

5. `convert_pta_checkpoint_for_mf()`（可选）  
   将 PTA 产出的 checkpoint 转成 MF 可加载格式。

从模型接入的视角看，Task1 至少涉及三类模型表示：

- `assets/runtime/model_config/<model>.yaml`：整网变异的基线配置
- `scripts/templates/pretrain_example/pretrain_mutated_<model>.sh`：PTA 训练脚本模板
- `assets/runtime/mf_templates/<model>.yaml`：MindFormers 模板（可选）

因此，一个新模型的接入通常拆成四层：

1. 扩展整网变异基线配置；
2. 扩展 PTA 模板脚本；
3. 扩展变异参数 schema 与脚本参数回填逻辑；
4. 如需 `pta_mf`，再补齐 MF 模板与权重转换支持。

---

## 3. 最小接入路径：先打通 `pta_msa`

如果目标是让新模型先进入 Task1 并稳定跑通 `pta_msa`，建议按以下顺序推进。

### 3.1 新增模型基线配置 YAML

在 `assets/runtime/model_config/` 下新增：

```text
assets/runtime/model_config/<model>.yaml
```

该文件名必须与 `MODEL_NAME` 严格一致。例如：

```text
assets/runtime/model_config/mygpt.yaml
```

如果文件不存在，Task1 在整网变异阶段会直接失败。

### 3.2 按当前工具约定组织 YAML 结构

当前整网变异主要识别以下几类字段：

- `TransformerConfig`
- `MLATransformerConfig`
- `extra_config`
- `get_gpt_layer_local_spec`
- `input`
- `attention_mask`

普通 Transformer 模型可参考如下骨架：

```yaml
TransformerConfig:
  num_layers: 24
  hidden_size: 2048
  ffn_hidden_size: 6144
  num_attention_heads: 16
  num_query_groups: 8
  tensor_model_parallel_size: 1
  pipeline_model_parallel_size: 1
  normalization: "RMSNorm"
  layernorm_epsilon: 1.0e-6
  attention_dropout: 0.0
  hidden_dropout: 0.0
  add_bias_linear: false
  init_method_std: 0.01

extra_config:
  seq_length: 4096
  max_position_embeddings: 4096
  position_embedding_type: "rope"
  rotary_base: 1000000
  micro_batch_size: 1
  global_batch_size: 32
  lr: 1.25e-6
  min_lr: 1.25e-7
  weight_decay: 0.1
  clip_grad: 1.0
  train_iters: 2000

get_gpt_layer_local_spec:
  num_experts: null
  moe_grouped_gemm: false
  qk_layernorm: false
  multi_latent_attention: false
  normalization: "RMSNorm"
  qk_l2_norm: false

input:
  shape: [32, 1, 2048]
  dtype: torch.float32
  device: "cuda"

attention_mask: default
```

如果模型属于 MLA / MoE 风格，则可以参考现有 `deepseekv3.yaml` 的组织方式。

### 3.3 明确哪些字段会真正参与图变异

这里有两个容易混淆的点：

1. 模型 YAML 可以很完整，但 Task1 最终只会抽取图构建所需的那部分配置。
2. 真正决定“某个参数能否被主动变异”的不是 YAML，而是 `assets/runtime/configs/mutation_schema.yaml`。

因此需要区分：

- **模型 YAML**：定义模型的基础配置；
- **mutation schema**：定义哪些参数有资格参与变异；
- **图构建过程**：只消费经过清洗后的 Transformer 侧配置。

换句话说，某个参数写进 YAML，并不等于它一定会在 Task1 中被变异。

## 4. PTA 模板脚本接入

### 4.1 新增模板脚本

在 `scripts/templates/pretrain_example/` 下新增：

```text
scripts/templates/pretrain_example/pretrain_mutated_<model>.sh
```

文件名同样必须与 `MODEL_NAME` 一致。例如：

```text
scripts/templates/pretrain_example/pretrain_mutated_mygpt.sh
```

### 4.2 模板脚本的最低要求

建议直接参考现有模板：

- `pretrain_mutated_qwen2.sh`
- `pretrain_mutated_qwen3.sh`
- `pretrain_mutated_deepseekv3.sh`

模板至少应满足以下要求：

1. 以 `pretrain_gpt.py` 为主入口；
2. 暴露 `CKPT_SAVE_DIR`、`CKPT_LOAD_DIR`、`DATA_PATH` 等基础变量；
3. 核心模型参数使用 `*_ARGS` 形式组织，便于后续自动改写；
4. 显式包含 tokenizer 参数；
5. 对于依赖 MoE / MLA / RoPE 特性的模型，相关参数位也要提前写进模板。

这是因为 `parallel_mutate` 在把 `mutating-<iter>.json` 回填到脚本时，并不是简单地“追加所有字段”。如果原模板里完全没有某个参数位，更新逻辑可能会直接跳过该参数。

例如，下面这些参数如果模板中不存在，可能不会被正确写回：

- `--moe-grouped-gemm`
- `--moe-aux-loss-coeff`
- `--moe-router-topk`
- `--expert-model-parallel-size`
- `--num-experts`

### 4.3 tokenizer 资源

模板中的 tokenizer 路径必须真实可用。当前仓库已有示例资源：

- `assets/runtime/tokenizers/llama2/`
- `assets/runtime/tokenizers/qwen2/`
- `assets/runtime/tokenizers/baichuan2/`

新增模型时可选两种方式：

1. 将 tokenizer 资源纳入仓库；
2. 在模板脚本中直接写外部绝对路径。

无论采用哪种方式，都必须保证：

- PTA 模板可以直接运行；
- `convert_pretrain_script.py` 能从 PTA 脚本中正确提取 tokenizer 参数。

## 5. 参数变异接入

### 5.1 更新 `mutation_schema.yaml`

如果新模型只是复用已有参数，例如 `num_layers`、`hidden_size`、`num_attention_heads`、`num_query_groups`，通常不需要改 schema。

如果希望新增模型的专属参数也参与 Task1 变异，需要修改：

```text
assets/runtime/configs/mutation_schema.yaml
```

重点关注两部分：

- `model_structure_args`
- `mutable_params`

接入规则：

1. 将新参数加入 `model_structure_args`；
2. 在 `mutable_params` 中定义取值范围或枚举集合；
3. 约束范围要贴近真实模型边界，避免生成明显非法配置。

### 5.2 理解“schema 改了但没变异”的原因

一个参数要真正出现在最终的 `mutating-<iter>.json` 中，通常至少要同时满足：

1. 该参数存在于本轮变异器接收到的 `base_config` 中；
2. 该参数在 `mutable_params` 中有定义；
3. 它被本轮候选池选中；
4. 采样出的新值与原值不同；
5. 后置约束修正没有把它改回去。

因此，下面两种情况都可能出现“看起来接入了，实际上没生效”：

- 参数只加进了 schema，但根本不在 Task1 使用的 `base_config` 中；
- 参数进入了候选池，但本轮采样后没有产生有效变化。

### 5.3 必要时补充 `parallel_mutate` 的参数合并逻辑

如果你发现：

- `mutating-<iter>.json` 已经发生变化；
- 但生成的 PTA 脚本没有体现出这些变化；

优先检查：

```text
utils/runtime/mutate_and_forward/parallel_mutate/main.py
```

重点关注两段逻辑：

1. `_merge_mutation_sections()`：决定变异结果如何回填到中间配置
2. `update_script_parameters()`：决定参数如何最终写回模板脚本

## 6. 让新模型进入 `pta_msa`

`pta_msa` 的准入规则相对直接。当前 Task1 会通过 `utils/runtime/model_support.py` 中的 `list_task1_template_supported_models()` 动态扫描：

```text
scripts/templates/pretrain_example/pretrain_mutated_*.sh
```

因此，对 `pta_msa` 而言，核心要求只有两个：

- 模型配置 YAML 存在；
- 模板脚本存在，且命名符合 `pretrain_mutated_<model>.sh` 规则。

也就是说，只要下面两份文件补齐，通常就已经具备进入 `pta_msa` 的最低条件：

- `assets/runtime/model_config/<model>.yaml`
- `scripts/templates/pretrain_example/pretrain_mutated_<model>.sh`

---

## 7. 让新模型进入 `pta_mf`

`pta_mf` 比 `pta_msa` 多两层要求：

1. 能生成 MF YAML；
2. 能将 PTA 权重转换为 MF 可加载格式。

### 7.1 新增 MF 模板

在 `assets/runtime/mf_templates/` 下新增：

```text
assets/runtime/mf_templates/<model>.yaml
```

建议做法是复制一个最接近的现有模板，再修改其中关键字段，例如：

- `model.model_config`
- `parallel_config`
- `context`
- `train_dataset`

### 7.2 检查 `mf_converter.py` 的参数映射

MF YAML 不是直接由模板得到，而是需要经过：

```text
utils/runtime/mf_converter.py
```

如果新模型依赖 PTA 侧的新参数，而这些参数没有出现在 `ARG_MAPPING` 中，就必须同步补齐。否则会出现：

- PTA 脚本参数正确；
- MF YAML 缺字段；
- 最终 MF 运行失败或配置不一致。

### 7.3 放开 Task1 的权重转换支持范围

在 `pta_mf` 模式下，还需要检查 `utils/runtime/model_support.py` 中的支持列表，例如：

```python
TASK1_WEIGHT_CONVERT_SUPPORTED_MODELS = ("qwen3", "deepseekv3")
TASK1_WEIGHT_CONVERT_MODEL_ALIASES = {
    "deepseekv3": "deepseek3",
}
```

如果新增模型要走 `pta_mf`，至少要：

1. 将其加入 `TASK1_WEIGHT_CONVERT_SUPPORTED_MODELS`；
2. 如有必要，在 `TASK1_WEIGHT_CONVERT_MODEL_ALIASES` 中添加别名映射。

### 7.4 确认上游 checkpoint 转换器真实支持该模型

这里只改本仓库白名单还不够。`convert_pta_checkpoint_for_mf()` 最终仍依赖：

- `scripts/runtime/convert.sh`
- `utils/runtime/convert_ckpt.py`
- 上游 `mindspeed_llm.tasks.checkpoint.convert_mg2hf`

如果上游转换器本身不支持该模型，那么本仓库即使放开了入口，运行时仍会在 checkpoint 转换阶段失败。

### 7.5 一个常见误区

**“已经有 MF 模板”不等于“Task1 已支持 `pta_mf`”。**

模板存在，只说明配置层可能已经准备好；并不代表：

- Task1 已放开模型白名单；
- 参数映射完整；
- checkpoint 转换可用；
- MF 实际可加载。

## 8. 推荐的接入顺序

为了降低排障成本，建议按下面顺序推进：

1. 新增 `assets/runtime/model_config/<model>.yaml`
2. 新增 `scripts/templates/pretrain_example/pretrain_mutated_<model>.sh`
3. 先跑通 `pta_msa`
4. 再决定是否需要扩 `mutation_schema.yaml`
5. 验证 `parallel_mutate` 是否正确改写脚本参数
6. 最后再补 `assets/runtime/mf_templates/<model>.yaml`
7. 单独验证 `pta_mf` 的 YAML 生成与 checkpoint 转换

---

## 9. 验收方式

### 9.1 验收一：只检查变异结果是否生成

优先确认是否生成：

```text
res/<model>/mutating-1.json
```

如果没有，优先检查：

- 模型配置 YAML 是否存在；
- YAML 字段是否符合当前解析约定；
- `mutation_schema.yaml` 是否引入非法约束。

### 9.2 验收二：检查 `pta_msa` 最小闭环

建议用最小配置启动，例如：

- `TOTAL_ITER=1`
- `MUTNM=1`
- `SAVE_STEPS=1`
- `LOAD_STEPS=1`
- `COMPARE_MODE=pta_msa`

重点检查：

- `res/<model>/mutating-1.json`
- `pta/<model>/pretrain_mutated_<model>-1.sh`
- `ms/<model>/pretrain_mutated_<model>-1.sh`
- `output/<timestamp>/iters/iter_1/` 下的归档产物

### 9.3 验收三：检查 `pta_mf`

只有在 `pta_msa` 已稳定后，再切换到：

```text
COMPARE_MODE=pta_mf
```

重点检查：

- `mf/<model>/pretrain_mutated_<model>-1.yaml` 是否生成；
- 转换后的 MF checkpoint 目录是否非空；
- MF 日志与 loss 对齐逻辑是否正常。

## 10. 常见问题

### 10.1 名字不一致

以下名称必须统一：

- `tasks["1"]["MODEL_NAME"]`
- `assets/runtime/model_config/<model>.yaml`
- `scripts/templates/pretrain_example/pretrain_mutated_<model>.sh`
- `assets/runtime/mf_templates/<model>.yaml`
- `utils/runtime/model_support.py` 中的模型名或别名

### 10.2 只加了 YAML，没有加模板脚本

这时整网变异阶段可能通过，但 `generate_pta_script()` 会失败。

### 10.3 只加了模板脚本，没有接入 schema

这时模型可以运行，但许多参数并不会真正参与变异。

### 10.4 `mutating-<iter>.json` 变了，但 PTA 脚本没变

优先检查：

- `_merge_mutation_sections()`
- `update_script_parameters()`

### 10.5 有 MF 模板，但 `pta_mf` 仍不可用

优先检查：

- `model_support.py` 是否放开；
- `convert_ckpt.py` 是否接受该模型名；
- 上游 checkpoint 转换器是否支持。

---

## 11. 结论

Task1 的关键不是“一次性把所有链路都补齐”，而是按层推进：

- 先补模型配置；
- 再补脚本模板；
- 先跑通 `pta_msa`；
- 最后再处理 schema、MF 模板与权重转换。

这样做的好处是：每一步都能明确知道失败发生在哪一层，而不是把所有问题混在一起排查。
