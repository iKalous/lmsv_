# 大模型泛化测试工具扩展说明（重构版）

## 1. 文档目标

本文用于指导后续开发者在 Ascend 环境下，为本工具扩展新的大模型测试能力，并确保扩展后的能力能够稳定接入如下测试链路：

- **Task1**：整网泛化变异
- **Task2**：模块内变异
- **Task3**：模块间变异
- **Task4 / Task5**：多模态模块级组合与单模块变异
- **Task6**：多模态整网变异

覆盖的运行形态包括：

- **PTA / MindSpeed**（动态图）
- **MSAdapter**（动态图对比链路）
- **MindFormers / MindSpore**（静态图对比链路）
- **MindSpeed-MM**（多模态）

---

## 2. 任务与运行模式总览

| 任务 | 目标 | 典型输入对象 | 主要链路 | 关键代码入口 |
|---|---|---|---|---|
| Task1 | 整网泛化变异 | 整个语言模型 | pta_msa / pta_mf | `utils/task/task1.py` |
| Task2 | 模块内变异 | TransformerBlock 内部子模块 | pta_msa / pta_mf | `utils/task/task2.py` |
| Task3 | 模块间变异 | 多个模块拼接后的图 | pta_msa / pta_mf | `utils/task/task3.py` |
| Task4 | 多模态模块间组合变异 | 多模态模块池 | PTA / MSA | `mutate.py` |
| Task5 | 多模态模块内变异 | 单个多模态模块 | PTA / MSA | `single_module_mutate.py` |
| Task6 | 多模态整网变异 | 完整多模态模型 | PTA / MSA，必要时衍生 MF 适配 | `utils/task/task6.py` |

### 2.1 术语统一

- **PTA**：指 MindSpeed / PyTorch 动态图链路
- **MSA**：指 MSAdapter 动态图对比链路
- **MF**：指 MindFormers / MindSpore 静态图链路
- **模块内变异**：在一个模块内部选取子模块进行替换或扰动
- **模块间变异**：将多个模块拼接成图并执行
- **整网变异**：对整网配置或整网结构进行泛化变异

### 2.2 推荐阅读顺序

- 只扩 **语言模型整网**：直接读第 6 节
- 只扩 **Task2 / Task3**：先读第 5 节，再读第 7、8 节
- 扩 **多模态模块组合或单模块变异**：读第 8 节
- 扩 **多模态整网 Task6**：读第 6.3 节和第 9 节

---

## 3. 通用扩展原则

无论扩展的是 Task1、Task2、Task3 还是多模态链路，建议统一遵循以下原则。

### 3.1 先判断改动落在哪一层

新增能力时，优先判断问题属于哪一层：

1. **配置入口层**  
   `genconf.py` / `webui.py` / `config.json`

2. **任务编排层**  
   `utils/task/task1.py` / `task2.py` / `task3.py` / `task6.py`

3. **图构建或模块构建层**  
   如 `subgraph.py`、`graph.py`、`modules/*.py`

4. **执行与对齐校验层**  
   如 `load_and_forward_*.py`、`run_mindformer.py`

不要一开始就改执行脚本。通常先确认**配置是否进得来、对象是否构得出来、再看执行是否对齐**。

### 3.2 命名必须全链路一致

下面这些名字在大多数链路中必须保持一致：

- `MODEL_NAME`
- `assets/runtime/model_config/<model>.yaml`
- `scripts/templates/pretrain_example/pretrain_mutated_<model>.sh`
- `assets/runtime/mf_templates/<model>.yaml`
- `utils/runtime/model_support.py` 中的模型名或别名
- 多模态场景下的 `MODEL_CONFIGS["your_model"]`

**名字不一致是最常见的接入失败原因。**

### 3.3 推荐接入顺序

对语言类模型，建议固定按下面顺序推进：

1. 先补配置
2. 再补模板
3. 先跑通最简单的 PTA 链路
4. 再接 MSA
5. 最后接 MF
6. 最后再补严格对齐和权重转换

对多模态模型，建议固定按下面顺序推进：

1. 先跑通 PTA
2. 再保证 PTA / MSA 参数严格对应
3. 最后再扩展变异参数池

## 4. 整网泛化扩展

### 4.1 主链路

一轮典型流程如下：

1. `run_mutate()`  
   `scripts/mutation/mutate-auto.sh` -> `utils/runtime/mutate_and_forward/mutate_graph-auto.py`

2. `generate_pta_script()`  
   根据 `mutating-<iter>.json` 和模板脚本生成 PTA 实际执行脚本

3. `convert_msa_script()`  
   将 PTA 脚本转换成 MSA 脚本

4. 可选 `generate_mf_script()`  
   将 PTA 参数映射到 MindFormers YAML

5. 可选 `convert_pta_checkpoint_for_mf()`  
   将 PTA checkpoint 转成 MF 可加载格式

### 4.2 动态图语言模型（pta_msa）

#### 4.2.1 最小接入必备文件

至少补齐下面两份文件：

```text
assets/runtime/model_config/<model>.yaml
scripts/templates/pretrain_example/pretrain_mutated_<model>.sh
```

如果缺任意一份，Task1 都无法形成最小闭环。

#### 4.2.2 模型配置 YAML 的基本要求

建议在 `assets/runtime/model_config/<model>.yaml` 中至少包含：

- `TransformerConfig` 或 `MLATransformerConfig`
- `extra_config`
- `get_gpt_layer_local_spec`
- `input`
- `attention_mask`

典型骨架如下：

```yaml
TransformerConfig:
  num_layers: 24
  hidden_size: 2048
  ffn_hidden_size: 6144
  num_attention_heads: 16
  num_query_groups: 8
  normalization: "RMSNorm"
  layernorm_epsilon: 1.0e-6
  attention_dropout: 0.0
  hidden_dropout: 0.0
  add_bias_linear: false
  init_method_std: 0.01

extra_config:
  seq_length: 4096
  max_position_embeddings: 4096
  micro_batch_size: 1
  global_batch_size: 32
  train_iters: 2000

input:
  shape: [32, 1, 2048]
  dtype: torch.float32
  device: "cuda"

attention_mask: default
```

#### 4.2.3 模板脚本的基本要求

模板脚本建议满足：

1. 以 `pretrain_gpt.py` 为主入口
2. 暴露 `CKPT_SAVE_DIR`、`CKPT_LOAD_DIR`、`DATA_PATH` 等变量
3. 模型参数按 `*_ARGS` 组织
4. 必须显式带上 tokenizer 参数
5. 如果依赖 MoE / MLA / RoPE 等特性，模板中要预留对应参数位

如果模板里完全没有某些参数位，即便 `mutating-<iter>.json` 已经变了，脚本回填逻辑也可能跳过这些参数。

#### 4.2.4 哪些参数会真正参与变异

请区分两个概念：

- **模型配置里存在**
- **Task1 真实会变异**

只有同时满足下面条件，参数才会真正被 Task1 变异：

1. 参数出现在当前 `base_config`
2. 参数出现在 `assets/runtime/configs/mutation_schema.yaml`
3. 参数被选入候选池
4. 采样结果与原值不同
5. 后置约束没有把它修回去

因此，**只改 YAML，不改 `mutation_schema.yaml`，很多参数不会变；只改 schema，但参数不在 `base_config` 中，同样不会变。**

#### 4.2.5 什么时候需要改 `parallel_mutate`

如果出现下面现象：

- `mutating-<iter>.json` 已变
- 但生成的 PTA 脚本没变

优先检查：

```text
utils/runtime/mutate_and_forward/parallel_mutate/main.py
```

重点关注：

- `_merge_mutation_sections()`
- `update_script_parameters()`

### 4.3 让新模型进入 `pta_msa` 支持列表

`pta_msa` 一般通过模板脚本动态扫描：

```text
scripts/templates/pretrain_example/pretrain_mutated_*.sh
```

因此其准入条件通常只有两个：

1. 模板脚本存在
2. 文件名满足 `pretrain_mutated_<model>.sh`

通常无需单独维护白名单。

### 4.4 静态图语言模型（pta_mf）

#### 4.4.1 与 pta_msa 相比新增的要求

`pta_mf` 比 `pta_msa` 至少多两件事：

1. 能生成 MF YAML
2. 能把 PTA checkpoint 转成 MF 可加载格式

#### 4.4.2 需要补的关键点

1. **新增 MF 模板**

```text
assets/runtime/mf_templates/<model>.yaml
```

2. **检查 `mf_converter.py` 的参数映射**
   - PTA 参数能否正确映射到 MF YAML
   - 重点看 `ARG_MAPPING`

3. **在 `model_support.py` 放开权重转换支持**
   - `TASK1_WEIGHT_CONVERT_SUPPORTED_MODELS`
   - `TASK1_WEIGHT_CONVERT_MODEL_ALIASES`

4. **确认上游 checkpoint 转换器真的支持该模型**
   - `scripts/runtime/convert.sh`
   - `utils/runtime/convert_ckpt.py`
   - 上游 `mindspeed_llm.tasks.checkpoint.convert_mg2hf`

#### 4.4.3 一个常见误区

**“有 MF 模板”不等于“Task1 已支持 pta_mf”。**

真正的准入条件是三者同时成立：

- MF 配置可生成
- 权重可转换
- MF 可加载

### 4.5 Task1 推荐验收方式

#### 验收 1：只看变异产物

确认是否生成：

```text
res/<model>/mutating-1.json
```

#### 验收 2：最小 `pta_msa` 闭环

推荐配置：

```text
TOTAL_ITER=1
MUTNM=1
SAVE_STEPS=1
LOAD_STEPS=1
COMPARE_MODE=pta_msa
```

重点检查：

- `res/<model>/mutating-1.json`
- `pta/<model>/pretrain_mutated_<model>-1.sh`
- `ms/<model>/pretrain_mutated_<model>-1.sh`

#### 验收 3：再测 `pta_mf`

在 `pta_msa` 稳定后，再切：

```text
COMPARE_MODE=pta_mf
```

重点检查：

- `mf/<model>/pretrain_mutated_<model>-1.yaml`
- MF checkpoint 是否非空
- MF 日志与 loss 对齐是否正常

### 4.6 多模态整网（Task6）

Task6 面向**完整多模态模型**的整网变异。

#### 4.6.1 主链路

`utils/task/task6.py` 一轮典型流程：

1. `run_mutation()`：生成变异配置
2. `run_pta_verify()`：PTA 环境验证
3. `run_msa_verify()`：MSA 环境验证
4. `analyze_results()`：结果分析

#### 4.6.2 最小接入步骤

1. 准备模型配置文件

```text
assets/mm_configs/
├── model_<your_model>.json
└── data_<your_model>.json
```

2. 创建 PTA 入口脚本

```text
scripts/runtime/mm_pta_<your_model>.sh
```

3. 创建 MSA 入口脚本

```text
scripts/runtime/mm_msa_<your_model>.sh
```

4. 创建真实执行脚本

```text
scripts/runtime/pta_<your_model>_real.sh
scripts/runtime/msa_<your_model>_real.sh
```

5. 注册到 `utils/task/task6.py`

```python
MODEL_CONFIGS = {
    "your_model": {
        "name": "YourModel",
        "base_config": "assets/mm_configs/model_your_model.json",
        "data_config": "assets/mm_configs/data_your_model.json",
        "pta_script": "scripts/runtime/mm_pta_your_model.sh",
        "msa_script": "scripts/runtime/mm_msa_your_model.sh",
        "mutation_output": "tmp/task6/mutation_results/your_model",
        "type": "train",  # 或 "inference"
    }
}
```

#### 4.6.3 多模态整网扩展时的关键约束

由于多模态模型通常依赖预训练权重，**部分结构参数不能随意变异**。  
扩展变异参数前，应先手动验证某个参数被修改后，预训练 / 推理脚本是否还能正常执行。

#### 4.6.4 变异参数池

常见位置：

```text
mm-new/net_mutation/mm_mutation_system.py
```

典型定义方式有三种：

```python
mutable_params_pool = {
  'mlp_ratio': {'min_val': 2.0, 'max_val': 8.0, 'min_factor': 0.7, 'max_factor': 1.5},
  'num_res_blocks': {'enum': [2, 3, 4]},
  'quantize_c_noise': {'enum': [True, False]},
}
```

- 区间 + 因子型
- 枚举型
- 布尔型

如果存在参数约束关系，需要补 `_select_and_mutate()` 中的约束逻辑。

## 5. Task2：模块内变异扩展

Task2 面向**一个模块内部的子模块**，例如某个 TransformerBlock 内的 `self_attention`、`mlp.linear_fc1` 等。

### 5.1 动态图链路（pta_msa）

#### 5.1.1 关键文件层次

- 配置入口：`genconf.py` / `webui.py` / `config.json`
- 任务编排：`utils/task/task2.py`
- 图构建：`utils/runtime/core/subgraph.py`
- PTA 执行：`utils/runtime/mutate_and_forward/load_and_forward_submodule-auto.py`
- MSA 执行：`utils/runtime/ms_mutate_and_forward/load_and_forward_submodule.py`

#### 5.1.2 接入步骤

1. 在 `assets/runtime/model_config/<model>.yaml` 中补模型配置
2. 放宽 `SUBMODULES` 的输入范围（若新增编号）
3. 在 `utils/runtime/core/subgraph.py` 的 `Graph.load(...)` 中补 `submodule_num -> node.block` 映射

例如：

```python
elif submodule_num == 11:
    node.block = transformer_block.layers[0].post_attention_layernorm
```

#### 5.1.3 通用检查项

- `COMPARE_MODE=pta_msa`
- `task2.py` 是否调用到正确的 PTA / MSA 脚本
- 结果文件是否生成：
  - `res/submodule_execution_pta.csv`
  - `res/submodule_execution_msa.csv`
- 日志是否正常：
  - `RuntimeError`
  - `attention配置严格对齐失败`

### 5.2 静态图链路（pta_mf）

#### 5.2.1 关键文件层次

- 配置入口：`genconf.py` / `webui.py` / `config.json`
- 任务编排：`utils/task/task2.py`
- 图构建：`utils/runtime/mf_mutate_and_forward/sub_graph.py`
- 执行与校验：`utils/runtime/mf_mutate_and_forward/load_and_forward_submodule.py`

#### 5.2.2 接入步骤

1. 放宽 `SUBMODULES` 范围（若需要）
2. 在 `sub_graph.py` 中补 `submodule_num -> MF 子模块实现` 映射
3. 在 `construct(...)` 中补对应形状处理
4. 如需新增 decoder 类型，补 `utils/runtime/OperatorSet.py`
5. 新增 `assets/runtime/mf_templates/<model>.yaml`
6. 在配置中设置：

```json
{
  "tasks": {
    "2": {
      "COMPARE_MODE": "pta_mf",
      "MF_ARGS_PATH": "assets/runtime/mf_templates/your_model.yaml",
      "ENABLE_MF_WEIGHT_LOAD": false
    }
  }
}
```

#### 7.2.3 建议联调顺序

1. 先 `ENABLE_MF_WEIGHT_LOAD=false`
2. 跑通整个流程
3. 再切到 `true` 验证权重加载一致性

## 6. 模块间变异扩展

### 6.1 动态图链路（pta_msa）

#### 6.1.1 关键文件层次

- 配置入口：`genconf.py` / `webui.py` / `config.json`
- 任务编排：`utils/task/task3.py`
- 图构建：`utils/runtime/mutate_and_forward/core/graph.py`
- PTA 执行：`utils/runtime/mutate_and_forward/load_and_forward_graph.py`
- MSA 执行：`utils/runtime/ms_mutate_and_forward/load_and_forward_graph.py`

#### 6.1.2 接入步骤

1. 在 `assets/runtime/model_config/<model>.yaml` 中补配置
2. 确认 `Graph.load(...)` 能正确读取和构建新节点
3. 对不兼容 `TransformerConfig` 的字段做别名映射

典型处理方式：

```python
FIELD_ALIAS = {
    "num_heads": "num_attention_heads",
    "eps": "layernorm_epsilon",
}
raw_cfg = {FIELD_ALIAS.get(k, k): v for k, v in raw_cfg.items()}
```

#### 6.1.3 关注点

- `attention参数加载统计`
- `attention未加载参数样例`

若出现系统性未加载，优先排查：

- 权重转换产物
- 节点参数命名
- 模块结构与图节点的对应关系

### 7.2 静态图链路（pta_mf）

#### 7.2.1 关键文件层次

- 图构建：`utils/runtime/mf_mutate_and_forward/graph.py`
- 执行与校验：`utils/runtime/mf_mutate_and_forward/load_and_forward_graph.py`

#### 7.2.2 接入步骤

1. 明确新增节点语义  
   默认：
   - `node_id == 0`：`embedding`
   - `node_id > 0`：`mutated_decoder`

2. 如果是新节点类型（如 adapter），必须同时扩展：
   - `Graph.load(...)`
   - `Graph.construct(...)`

3. 若新字段影响数值路径，需要补齐：
   - `ATTENTION_ALIGN_FIELDS`
   - `DECODER_CRITICAL_ALIGN_FIELDS`
   - `DECODER_FOCUS_FIELDS`

4. 验证参数加载与权重对齐是否完整

#### 7.2.3 典型伪代码

```python
if node_id == 0:
    node.str_op = "embedding"
elif node_type == "adapter":
    node.str_op = "adapter"
else:
    node.str_op = "mutated_decoder"
```

执行分支也要同步补：

```python
if cur_node.str_op == "embedding":
    output = cur_block(input_ids=input_ids, position_ids=position_ids)
elif "decoder" in cur_node.str_op:
    output = cur_block(input_data, attention_mask)
elif cur_node.str_op == "adapter":
    output = cur_block(input_data)
```

## 8. 多模态模块级扩展

### 8.1 主流程

- `mutate.py`：模块间组合变异
- `single_module_mutate.py`：模块内变异

两条流程都依赖：

- `modules.json`：模块池
- `modules/*.py`：模块类型与构建逻辑
- `templates/*.py`：模板与连接范式

### 8.2 扩展一个新的模块类型

以 `image_encoder` 为例，至少需要改四处：

1. `modules/<type>.py`  
   定义基类、构建器字典、注册装饰器

2. `modules/pool.py`  
   增加对应的 DictPool 与 `build()` 逻辑

3. `modules.json`  
   增加新的顶层键，例如 `image_encoders`

4. `mutate.py`  
   在 `register_all_modules()` 中注册该类型

### 8.3 在某个模块类型下扩展一个具体模块

以 `llava` 的 `image_encoder` 为例：

1. 在 `modules/image_encoder.py` 中实现子类并用 `@register_image_encoder("llava")` 注册
2. 在 `modules.json` 中新增 `llava` 的配置
3. 检查 `config_preprocess()` 不会破坏该模块的关键字段
4. 执行 `python mutate.py` 验证是否能被随机选中并跑通前向 / 反向

### 8.4 扩展新的模板

当现有模板不适配新组合模式时：

1. 在 `templates/` 下新增模板类
2. 至少实现：
   - `select_modules()`
   - `instantiate()`
   - `forward()`
   - `dump_graph()`
3. 在 `mutate.py` 的 `register_all_templates()` 中注册

### 8.5 接入模块内变异

对应 `single_module_mutate.py`，至少补两类内容：

1. **变异参数范围**
   - 文件：`single_module_mutate_dict.json`

2. **单模块模板**
   - 参考：
     - `templates/single_text_decoder_template.py`
     - `templates/single_image_encoder_template.py`

模板至少建议实现：

- `get_module_type()`
- `get_module_name()`
- `get_module_config()`
- `set_module_config()`

## 9. 通用验收与排查

### 9.1 通用验收顺序

无论扩展哪个任务，建议固定按下面顺序验收：

1. **配置是否被接收**
2. **对象是否能构建**
3. **脚本是否能生成**
4. **最小迭代是否能执行**
5. **日志是否通过**
6. **结果文件是否生成**
7. **严格对齐开关是否通过**

### 9.2 常见日志检查点

#### 动态图链路

- `RuntimeError`
- `attention配置严格对齐失败`

#### 静态图链路

- `RuntimeError`
- `attention配置严格对齐失败`
- `decoder配置严格对齐失败`

### 9.4 常见问题

#### 问题 1：名字不一致

表现：不同阶段报“找不到模型”。  
处理：统一模型名、模板名、配置名、别名。

#### 问题 2：只改了 YAML，没改模板

表现：配置解析可能通过，但脚本生成失败。  
处理：补 `pretrain_mutated_<model>.sh`。

#### 问题 3：`mutating-<iter>.json` 已变，但生成脚本没变

表现：看起来“变异失效”。  
处理：检查 `parallel_mutate/main.py` 的合并和脚本更新逻辑。

#### 问题 4：有 MF 模板，但 `pta_mf` 仍不可用

表现：MF YAML 能生成，但后续失败。  
处理：检查 `model_support.py`、`mf_converter.py`、checkpoint 转换器、上游模型支持。

#### 问题 5：多模态模型一改参数就炸维度

表现：推理或训练阶段 shape mismatch。  
处理：先做单参数手动验证，确认哪些参数允许变异，再加入参数池。

## 11. 最终建议

如果后续还会持续演进这份文档，建议继续保持下面的写法规则：

1. **优先按 Task 组织，而不是按“动态图 / 静态图 / 多模态”三种轴混排**
2. **先写“最小接入路径”，再写“增强能力”**
3. **通用检查项统一放在末尾，不要在每章重复**
4. **每章都明确：改哪些文件、为什么改、如何验收**
5. **代码片段只保留关键骨架，避免把实现细节全文复制进去**

这样这份扩展文档会更适合作为后续维护文档，而不是一次性笔记。
